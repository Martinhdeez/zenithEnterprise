# F1 — Tenancy and RLS context

**Date:** 2026-08-01
**Status:** planned
**Milestone:** M0 (foundations) / M3 (exposure)
**Branch:** `feat/f1-tenancy`
**Specification:** `.artifacts/specs/2026-07-27-mvp.md` §2.4, §3.4, §4
**Depends on:** F0 — schema, policies and `zenith_app` role already exist

---

## 1. Goal

Turn the RLS machinery that F0 put in the database into something the application can actually use, and make it **impossible to bypass by accident**.

F0 proved the policies work when a test sets the GUCs by hand. F1 provides the only supported way for application code to obtain a session, and guarantees that no other way exists.

**Exit criterion:** a tenant can be created, its context resolved, and every subsequent query is scoped without any caller ever writing `tenant_id` in a `WHERE` clause.

---

## 2. Why this comes before `auth`

It is tempting to build users and login first, because that is what you can demo. The order is deliberate:

**Every other feature will open sessions.** If `documents` and `auth` are written before the session contract is fixed, each of them invents its own way to reach the database, and the guarantee becomes a convention. Written in this order, the only session constructor that exists is the safe one.

**RLS context is not authentication.** A background worker reindexing a tenant's corpus has a tenant context and no user at all. Coupling context to login would make that case impossible to express without a bypass — and bypasses are what leaks are made of.

---

## 3. Scope

### 3.1 Domain model

`Tenant` already exists as a table from F0. F1 adds the domain layer around it:

| Component | Responsibility |
|---|---|
| `TenantRepository` | Reads within a context. **Cannot create tenants** — see below |
| `TenantService` | Creation and lookup, using the owner connection |
| `TenantContext` | Immutable value object: `tenant_id` + reachable `label_ids` |

**Creating a tenant is a privileged operation and lives apart.** It cannot happen inside a tenant context, because no context exists yet — this is the cold-start problem from §2.4. So tenant creation uses the owner connection and is exposed only to the CLI, never to a request handler. That asymmetry is the point, not an inconvenience: the one operation that escapes RLS is isolated in one place that is easy to audit.

### 3.2 Session contract

The single supported entry point, already sketched in F0:

```python
async with tenant_session(tenant_id, label_ids) as session:
    ...
```

F1 hardens it:

- **`TenantContext` replaces the loose pair of arguments.** Passing `tenant_id` and `label_ids` as two separate parameters invites a call site that passes one and forgets the other, which silently widens visibility to the whole tenant.
- **Owner sessions are explicitly named.** `owner_session()` exists, is documented as bypassing RLS, and is used only by the CLI and migrations. A grep for it is a complete audit of the bypass surface.
- **`verify_rls_active` moves into a reusable startup check** so the worker runs it too, not just the API. Right now only the API checks.

### 3.3 Guard against the failure mode we already know about

F0 left one real hole: the schema does not use `FORCE ROW LEVEL SECURITY`, so connecting as the owner disables isolation with no symptom. The API checks this at startup. F1 extends the guard:

- The **worker** performs the same check before consuming any job.
- The check reports which role it connected as, so a misconfiguration is one log line instead of an investigation.

### 3.4 Out of scope

- Users, roles, permissions — F2.
- Access labels as a manageable entity — F3. F1 accepts `label_ids` in the context, but nothing creates labels yet.
- HTTP endpoints. F1 exposes no routes: there is no authentication to derive a tenant from. Tenancy becomes reachable over HTTP in F2.
- The `zenith` CLI. F1 provides the service the CLI will call; the CLI itself is M3.

## 4. Tests

Inside the feature (`app/features/tenancy/tests/`):

| Test | What it protects |
|---|---|
| Creating a tenant persists it and returns it | Basic behaviour |
| Duplicate tenant name is rejected | `UNIQUE` constraint surfaces as a domain error, not a raw driver error |
| `TenantRepository` refuses a session with no context | The guard from F0 is reachable from the domain layer |
| A context with no labels sees only unlabelled documents | Default visibility is the narrow one |
| `TenantContext` is immutable | A mutated context mid-transaction would silently widen scope |

In `tests/integration/`:

| Test | What it protects |
|---|---|
| The worker refuses to start with owner credentials | Extends the F0 API guard to the second process |
| Two concurrent sessions with different contexts do not see each other's rows | The GUC is transaction-local, not connection-local. If this fails, connection pooling leaks context between tenants — the worst possible bug in this system |

**The second one is the important test in F1.** `set_config(..., true)` is transaction-scoped, but that is an assumption worth proving under a real pool rather than trusting. If it were connection-scoped, a pooled connection returned after one tenant's request would carry their context into the next tenant's request.

---

## 5. Risks

| Risk | Mitigation |
|---|---|
| Context leaking between pooled connections | The concurrency test above. If it fails, the fix is resetting GUCs on connection checkin |
| `owner_session` spreading beyond the CLI | Named explicitly so it is greppable; reviewed on every PR that adds a call |
| Tenant creation ending up in a request handler | It only accepts the owner engine, so a request-scoped session cannot call it |
