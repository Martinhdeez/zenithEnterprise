# F3 — Access labels

**Date:** 2026-08-03
**Status:** planned
**Milestone:** M3
**Branch:** `feat/f3-labels`
**Specification:** `.artifacts/specs/2026-07-27-mvp.md` §2.2 (RF-04.2), §3.4
**Depends on:** F1 — `TenantContext`; F2 — `requires(...)`, label resolution from roles

---

## 1. Goal

F2 reads `role_labels` to build a context. **Nothing writes it.** Every user in every
tenant currently reaches zero labels, which means the second RLS level is enforced and
permanently empty.

F3 makes labels real: create them, assign them to roles, assign them to documents, and
keep the denormalised copies correct.

**Exit criterion:** an administrator creates a label, gives it to a role, applies it to a
document, and a user of that role can see the document while a user of another role
cannot — with the refusal coming from Postgres, not from application code.

---

## 2. Scope

### 2.1 The label entity

`access_labels` already exists: `id`, `tenant_id`, `name`, unique per tenant. F3 adds the
operations, all behind `requires("labels.manage")`.

```
POST   /labels              create
GET    /labels              list
PATCH  /labels/{id}         rename
DELETE /labels/{id}         delete, with the guard in §2.4
PUT    /roles/{id}/labels   set which labels a role reaches
PUT    /documents/{id}/labels   set a document's labels
```

Full role CRUD stays in M3. F3 delivers only the label side of the relation, because that
is what the second RLS level needs.

### 2.2 The denormalisation, and why it is a trigger

The RLS policy on `documents` reads `documents.label_ids`, an array copy of
`document_labels`. It exists because a policy on `documents` that read `document_labels`,
whose own policy reads `documents`, makes Postgres abort on mutual recursion. The copy is
not an optimisation; the direct version does not run.

The copy is therefore load-bearing for security, and **a copy that drifts from its source
is a leak or an outage, depending on the direction it drifts.**

| Sync mechanism | Verdict |
|---|---|
| Application code updates both | **No.** Every path that touches labels must remember. One that forgets produces a document visible to a whole tenant, silently. |
| Generated column | Impossible. It reads another table. |
| **Database trigger** | **Yes.** |

This is the same argument that chose RLS over `WHERE` clauses: the guarantee must not
depend on the discipline of whoever writes the next query. A trigger on `document_labels`
recomputes `documents.label_ids`, and a trigger on `documents.label_ids` propagates to
`chunks.label_ids` — which carry their own copy so the tenant and label filters can apply
inside the vector query without a join penalising the HNSW index.

```
document_labels  --trigger-->  documents.label_ids  --trigger-->  chunks.label_ids
```

**Cost to measure, not assume.** A label change on a 3,000-page document rewrites every
chunk row for it. At the §2.12 ceiling that is a five-figure `UPDATE` inside a 10-second
`statement_timeout`. Measured in F3, and if it does not fit, the propagation to `chunks`
moves to the queue — which is available, and which changes the security story, because
a queued update means a window where `chunks` and `documents` disagree. Preference is
strongly for keeping it synchronous.

### 2.3 The trigger has to bypass RLS, and that is a decision

The policy on `documents` carries `WITH CHECK (label_ids = '{}' OR label_ids && zenith_current_labels())`.
So an administrator holding `labels.manage` but not reaching *Finance* who removes the
last non-Finance label from a document would produce a row they can no longer see — and
the `WITH CHECK` rejects the write.

Two options:

1. **Accept it.** You cannot move a document out of your own reach. Safe, and surprising:
   an administrator managing labels for a team they are not in is blocked from doing their
   job, with an error about a row they never mentioned.
2. **Make the trigger `SECURITY DEFINER`.** The trigger stops being an access decision and
   becomes what it actually is: a consistency mechanism maintaining a derived value.

**Recommendation: option 2.** The authorisation decision belongs where the user acts — RLS
on `document_labels` governs whether they may change the mapping at all, and
`requires("labels.manage")` governs whether they may reach the endpoint. Re-deciding it in
the trigger means deciding it twice, in a place with less information.

This adds a second `SECURITY DEFINER` object, so **technical-decisions.md §5.1 must be
updated in the same commit.** That section claims to be the complete list of routes around
RLS, and a list that is quietly incomplete is worse than no list.

### 2.4 Deleting a label is the dangerous operation

The policy reads:

```sql
label_ids = '{}'::uuid[] OR label_ids && zenith_current_labels()
```

**An unlabelled document is visible to the entire tenant.** That is deliberate — §2.2
chose it because denying by default makes the product look broken — but it means:

> Deleting a label that is the only label on a document makes that document visible to
> everyone in the tenant.

A delete that *widens* access, silently, through a cascade. This is F3's equivalent of the
lockout: the operation looks administrative and its consequence is a leak.

**`DELETE /labels/{id}` is refused while any document carries it**, with a message saying
how many. Reassignment first, deletion after. Roles are not part of the guard — removing a
label from a role only narrows what that role reaches, which fails closed.

### 2.5 The tenant default label

§2.2 requires the uploader to choose a label at upload time, with a **default configurable
by the tenant administrator**. Without it, F4 has to invent one or leave documents
unlabelled, and unlabelled means tenant-wide.

F3 adds `tenants.default_label_id` (nullable, `ON DELETE SET NULL`) and the endpoint to set
it. F4 consumes it. The column belongs with the entity that owns labels, not with upload.

### 2.6 Out of scope

- Full role CRUD — M3.
- Document upload — F4. F3's document-labelling endpoint is tested against rows inserted
  directly, because there is no upload yet.
- Label hierarchies or inheritance — rejected in §2.2 and not reopened.
- Any AI involvement in assigning labels. See `.artifacts/ideas/2026-08-01-result-grouping.md`:
  labels are security, grouping is presentation, and a model that hallucinates a tag must
  never become a model that grants access.

## 3. Data

Migration `0003`:

- `tenants.default_label_id` — nullable FK to `access_labels`, `ON DELETE SET NULL`.
- `zenith_sync_document_labels()` — trigger on `document_labels`, recomputes
  `documents.label_ids`. `SECURITY DEFINER`, `search_path` pinned.
- `zenith_sync_chunk_labels()` — trigger on `documents`, propagates to `chunks` when
  `label_ids` actually changed. Guarded by `IS DISTINCT FROM` so unrelated updates to a
  document do not rewrite its chunks.

No new tables. `document_labels` and `role_labels` exist from F0.

## 4. Tests

| Test | What it protects |
|---|---|
| Adding a `document_labels` row updates `documents.label_ids` | The copy is maintained at all |
| Removing one updates it | Drift in the other direction |
| Deleting a label cascades into both the join table and the array | FK cascade fires the row trigger |
| `documents.label_ids` change propagates to `chunks.label_ids` | The vector-query filter agrees with the document |
| An unrelated update to a document does not rewrite its chunks | The `IS DISTINCT FROM` guard; without it, every status change during ingestion rewrites every chunk |
| **A label reachable by a role makes the document visible to that role, end to end** | **The F2/F3 join: role → context → RLS → rows** |
| A role without the label sees nothing, and cannot infer existence from a count | Non-inference, §2.2 |
| Deleting a label still on a document is refused | §2.4 — the delete that widens access |
| A label of another tenant cannot be assigned to a document | `WITH CHECK` on `document_labels` |
| Every label endpoint refuses without `labels.manage` | The dependency is wired |
| Sync cost on a document at the page ceiling | §2.2 — measurement, not a gate |

**The end-to-end visibility test is the one that matters.** Every other test here checks a
mechanism; that one checks the mechanisms compose. F2 proved a context carries the right
labels, F0 proved policies filter on labels, and neither proves that assigning a label to a
role actually lets a user read a document.

Verification by sabotage, as in F1 and F2: disabling the trigger must fail the sync tests,
and widening the delete guard must fail §2.4's.

## 5. Risks

| Risk | Mitigation |
|---|---|
| The denormalised copy drifts from `document_labels` | A trigger, not application code. Tested in both directions. |
| Deleting a label makes documents tenant-visible | Deletion refused while documents carry it |
| Label propagation to `chunks` exceeds `statement_timeout` on a large document | Measured in F3. Queue only if it does not fit, and only with the disagreement window written down |
| The trigger's `SECURITY DEFINER` becomes a habit | §5.1 updated in the same commit; it stays a list of three, now four, not an unbounded set |
| Label *names* leak information | RLS on `access_labels` is tenant-wide, so any user can list them. "Project Titan acquisition" is itself a disclosure. **Open question — see §7.** |
| Ingestion rewrites every chunk on every status change | `IS DISTINCT FROM` guard, with its own test |

## 7. Settled: label listing is restricted

**Decided 2026-08-03.** A caller without `labels.manage` sees only the labels their own
roles reach. Holders of `labels.manage` see all of them, because managing a set you cannot
enumerate is not management.

The reasoning: a label named *"Project Titan acquisition"* discloses something merely by
existing. §2.2's non-inference rule is written about documents, but the spirit of it
applies to anything that reveals what exists. A user has no reason to enumerate labels
they cannot reach, and the cost of deciding it now is one `WHERE` — deciding it later is a
breaking API change.

**This is application-level, not RLS.** The policy on `access_labels` stays tenant-wide,
because the label rows themselves have to be readable for the joins that resolve a
context. The restriction lives in the listing endpoint, which means it is exactly the kind
of rule that can be forgotten — so it gets its own test rather than relying on the
database to catch it.
