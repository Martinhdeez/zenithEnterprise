**Date:** 2026-08-03
**Status:** planned
**Milestone:** M0 (resequenced ahead of F4)
**Branch:** `feat/m0-baseline`
**Specification:** `mvp.md` §8, `iteration-plan.md` §M0, `project-state.md` §7

---

## 1. Why this comes before F4

M0 was always in the plan. It was attached to **F8**, ninth of nine.

That ordering assumes hybrid retrieval works. Every decision since — pgvector with HNSW,
ParadeDB for BM25, RRF fusion, the reranker, per-page parser routing — rests on that
assumption, and none of it has been tested against a single real document. If retrieval
disappoints on a scanned manual, F4 through F7 were built on something nobody checked.

Finding that out now costs days. Finding it out after F7 costs the quarter.

**This is resequencing, not new scope.** The measurements below are the ones `mvp.md` §8
already refers to as "M0 baseline", and the partitioning comparison `project-state.md` §7
already defers to M0. What changes is when.

## 2. Scope

### 2.1 The corpus — public, and deliberately hard

**The constraint:** design partners are still TBD (`iteration-plan.md` §306), so there is
no customer corpus, and RNF-07 forbids using one with cloud APIs even when it exists.

**The answer:** 20–30 public PDFs chosen for difficulty rather than convenience.

| Category | Why it is in the set |
|---|---|
| Scanned documents, skewed text | The failure mode a clean test set never reveals |
| Two-column layouts | Naive extraction interleaves the columns and produces nonsense |
| Financial tables | The case §1 of the tables idea exists for; also the hardest for chunking |
| Long technical manuals (500+ pages) | Where chunking strategy starts to matter |
| Regulations and filings (10-K, EU directives) | Dense, cross-referential, close to real enterprise documents |

The rule: **harder than what a customer will upload.** A pipeline that survives a badly
scanned manual survives a clean contract. The reverse is not true.

Stored as a manifest of URLs plus checksums, not as committed binaries — the repository
does not grow by 500 MB, and anyone can rebuild the corpus.

### 2.2 The question set

50 questions with known answers, each recording the document and page the answer lives on.

**On RNF-07.** The prohibition is on cloud APIs applied to *customer* documents. These are
public filings, so a cloud model may draft the questions, which makes 50 an afternoon
rather than a week. **The moment a design partner's corpus arrives, local-only applies
absolutely.** That distinction is written here so nobody has to re-derive it under time
pressure.

Every drafted question is verified by hand against the source. An unverified question set
measures the drafting model, not the retrieval system.

Question types, deliberately mixed:

- **Factual lookup** — the answer is one passage. The baseline case.
- **Cross-document** — the answer requires two sources. Tests fusion, not just ranking.
- **Table arithmetic** — currently expected to fail. Recorded as the baseline the tables
  work in F5 has to beat.
- **Unanswerable** — the corpus does not contain the answer. Tests abstention, which
  `mvp.md` §8 gates at 0% fabrication.

### 2.3 The tracer bullet — deliberately bad

```
PDF → pdfplumber           (no per-page routing, no docling)
    → fixed-size chunks    (no context prefix, no bounding boxes)
    → BGE-M3               (the real model; runtime differs by host, see §6)
    → chunk_embeddings     (the real schema)
    → BM25 + vector + RRF  (no reranker)
    → recall@k
```

**Every simplification is a variable held constant.** If retrieval works well here, the
reranker and contextual chunking are refinement. If it works badly, we learn *which stage*
is weak before building four features on top of it.

No queue, no API, no RLS wiring, no upload. A script that reads files from disk.

### 2.4 The harness is permanent

`iteration-plan.md` §7 rejected a throwaway spike in favour of "a permanent harness instead
of disposable code". The pipeline is disposable; the corpus, the question set and the
measurement code are not. They live in `eval/`, which the specifications already reserve,
and every later iteration re-runs them.

That is what makes "no degradation versus the M0 baseline" a checkable statement rather
than a hope.

## 3. Measurements

### 3.1 Retrieval quality

| Measurement | Why |
|---|---|
| Recall@50, Recall@8 | The baseline every later gate is stated against |
| MRR | Recall says the passage was retrieved; MRR says it was ranked usefully |
| Recall@50 at 100% / 20% / 5% corpus reach | **A gate in `mvp.md` §8**: no drop greater than 5%. This is the label-filtering risk that motivated the whole partitioning discussion |
| Recall by question type | Where it fails matters more than that it fails. Table questions failing is expected; factual lookup failing is an emergency |
| Abstention on unanswerable questions | The 0%-fabrication gate has no meaning without a measured starting point |

### 3.2 Partitioned versus filtered

`project-state.md` §7 deferred the per-tenant partitioning decision to M0. The comparison
is run here: `chunk_embeddings` filtered by `tenant_id` against the same table partitioned
by it, one HNSW index per partition.

**A decision taken on numbers in week four with an empty database, rather than on intuition
with customers in production.** It is a migration either way, so the option stays cheap.

### 3.3 Resources — the customer hardware spec

We have never written the minimum hardware a customer needs, and it is the first question
any IT department asks. We cannot write it because we do not know the cost per document.
M0 is when we find out.

**These run on the VPS, not on the development machine, and that is not a detail.** See §6:
`text-embeddings-inference` ships no arm64 build, so on Apple Silicon it runs under
emulation. Numbers taken there would be worse than a cheap Linux box and wrong in a way no
correction factor fixes, because emulation overhead is not a constant. The VPS is x86_64
Linux running the real TEI image — the architecture a customer actually deploys on.

Slow is acceptable here: peak RAM and time-per-100-pages are measured once, not iterated on.

| Measurement | Turns into |
|---|---|
| RAM peak during ingestion, per 100 pages | "For N documents you need X GB" |
| Wall-clock parse / chunk / embed, per 100 pages | "Expect your initial import to take Y hours" |
| Disk: `pages`, `chunks`, `chunk_embeddings` per 100 pages | Storage sizing, and the cost of a second vector space during reindexing |
| HNSW build time and index size | Whether reindexing is an overnight job or a weekend one |

### 3.4 Latency is measured, not gated

`mvp.md` §8 gates p95 retrieval + fusion + reranking at **< 500 ms**. That gate **cannot be
validated here**, and pretending otherwise would be worse than not measuring.

The M4 Pro this runs on is not customer hardware, and a number recorded now would be
compared against later by someone who has forgotten where it came from. `iteration-plan.md`
§290 already says it: *"In M0 latency is a measurement; the real scale gate arrives in
iteration 4."*

So latency is recorded **with the hardware written next to it**, always, and never quoted
without it.

## 4. What the result means

**The headline metric is Recall@8 over factual and cross-document questions only.**
Table and unanswerable questions are excluded from it, and this is not a convenience:

- **Table questions are expected to score near zero.** The tracer bullet runs `pdfplumber`
  with no Docling routing, so tables are flattened into number soup by design. Including
  them would drag the average down by however large that slice is and trigger a false
  "something fundamental is wrong" — when the real finding is "extraction needs Docling",
  which we already knew and F5 already plans.
- **Unanswerable questions have no recall at all.** The metric is undefined when no correct
  passage exists; they measure *abstention*. Averaging them in scores correct behaviour as
  failure.

Both are recorded separately, as baselines their own later work has to beat.

| Recall@8 (factual + cross-document) | Reading | What happens next |
|---|---|---|
| **> 85%** | Hybrid retrieval works. The architecture is sound. | F4–F7 proceed with confidence. |
| **60–85%** | Works; needs the pieces we deliberately removed. | Proceed. Reranking and contextual chunking now have a measured baseline to beat, which is exactly what they are for. |
| **< 60%** | Something fundamental is wrong. | **Stop.** Diagnose by stage — parsing, chunking, embedding or fusion — before building anything on top. |

**The third row is the entire point of doing this now.** It is also the only row where M0
saves more than it costs, which is why the work is scoped to days and the pipeline is
allowed to be ugly.

Diagnosis by stage is possible because the pipeline is a straight line: dump the extracted
text and read it; check whether the target passage is in the corpus at all; run BM25 alone
and vectors alone before fusing. A failure localises instead of being "the RAG is bad".

## 5. What M0 deliberately does not do

- **No quality gate.** M0 produces baselines; it cannot fail against a threshold that does
  not exist yet. `iteration-plan.md` §64: *"few gates and many measurements, and that is
  correct."*
- **No latency gate.** See §3.4.
- **No production code.** The pipeline is not the ingestion feature. F5 is written properly,
  with the queue, idempotency and bounding boxes.
- **No UI.**
- **No reranker.** Held constant on purpose, and it also keeps the VPS option open — the
  reranker is a cross-encoder scoring 50 candidates per query, which is the heaviest thing
  in the stack on CPU.

## 6. Where it runs

**Split, because the two halves need different things.**

| | Host | Runtime |
|---|---|---|
| Quality — §3.1, §3.2 | M4 Pro, 24 GB | BGE-M3 via PyTorch with the MPS backend |
| Resources — §3.3 | VPS, x86_64 Linux, 4.4 GB | BGE-M3 via TEI, the production image |

**Why not TEI on the Mac.** `text-embeddings-inference:cpu-1.8` publishes `linux/amd64`
only. On arm64 it runs under emulation in Docker Desktop, which for compute-bound inference
is commonly 5–20× slower. Numbers from there would be worse than the cheap VPS and
misleading in both directions, and no correction factor repairs it: emulation overhead is
not a constant.

**Why swapping the runtime does not invalidate the quality measurement.** PyTorch and TEI
serve the *same weights*. The same text produces the same vector, so the same query returns
the same ranking. Recall, MRR and the partitioning comparison are unaffected by which
process computed the embedding — which is exactly the property that lets the quality half
run anywhere at all.

What this does cost: the production serving path is TEI, and running it only on the VPS
means it is exercised on one architecture during M0. That is fine — the runtime is not what
M0 is testing — but it is written down rather than discovered later.

**Deliberately not here:** `zenith diagnose`. It is production CLI code, and M0 is a
laboratory branch whose pipeline is disposable by design. Mixing the two puts permanent
code and throwaway code in one review, where the throwaway half gets the scrutiny the
permanent half needed. It ships as its own small PR before this branch starts.

## 8. Risks

| Risk | Mitigation |
|---|---|
| The corpus is not representative of a real customer's documents | Deliberately harder than expected. Revisited the moment a design partner is confirmed (`iteration-plan.md` §311) |
| The question set measures the drafting model, not retrieval | Every question verified by hand against the source |
| M0 becomes a project | Days, not weeks. The pipeline is allowed to be ugly; only corpus, questions and measurement survive |
| A bad result is rationalised away | The thresholds in §4 are written **before** the numbers exist. That is the whole reason they are in this document |
| Latency numbers escape their hardware context | Never recorded without the machine beside them |
| Resource numbers taken under emulation become a customer hardware spec | §3.3 runs on x86_64 Linux only; the statement names the architecture it was measured on |
| Table and unanswerable questions drag the headline average into a false alarm | Excluded from it by definition, recorded separately as their own baselines |
