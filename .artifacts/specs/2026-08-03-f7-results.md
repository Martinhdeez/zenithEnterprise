# F7 results — the reranker closed the gap entirely

Measured with `ZENITH_EVAL_RERANK=1 uv run python -m eval.production`: the same corpus, the
same 36 questions, through `SearchService` with the cross-encoder in the path.

## Result: PASS, at the ceiling

| | M0 tracer bullet | F6 production | **F7 reranked** |
|---|---|---|---|
| **Recall@8** | 75% | 80% | **95%** |
| Recall@50 | 95% | 95% | 95% |
| Document-level Recall@8 | 100% | 100% | 100% |

The target was ≥90%. **Recall@8 now equals Recall@50.**

That equality is the finding, not the 95%. It means the reranker recovers *everything* the
candidate set contains — there is no longer a single question whose answer sits at rank 9–50
waiting to be lifted. The ordering problem is solved. What remains is a **retrieval** problem:
5% of questions have no correct passage in the top 50 at all, and no reranker can help them.

**The reranker has nothing left to gain.** Any further improvement has to come from the
candidate set: better chunking, a better embedder, or `pg_search`'s BM25 in place of
`ts_rank_cd`.

## By question type

| Type | F6 | **F7** | |
|---|---|---|---|
| factual | 86.7% | **100%** | every one |
| cross-document | 60.0% | **80.0%** | the hard half |

## The identifier fix worked, and it needed both halves of the change

Identifier questions went from **0 of 6 to 5 of 6**, and two of those recoveries could only
have come from the fusion change rather than the reranker:

- `identifier-regulation-2022-2065` — **rank 1**
- `identifier-oj-page` — **rank 1**, and it was not in the fused top-50 *at all* before

The second is the one that proves the point. No reranker can promote a passage that was
never a candidate. Making the candidate set the **union** of both halves is what put it in
front of the cross-encoder; the cross-encoder then put it first.

`identifier-usc-citation` still misses at rank 50. That is a genuine retrieval failure — the
passage is not being found by either half — and it belongs to whatever improves the
candidate set, not here.

Note that `identifier` remains excluded from the headline. It was excluded before it scored
0% and before it scored 83%, which is the only reason either number can be quoted without
suspicion.

## Tables did not move, exactly as M0 predicted

80% before, 80% after. M0 recorded this in advance: **recall cannot measure comprehension.**
Retrieval finds the page whether or not the table on it survived extraction, so no retrieval
metric will ever show what Docling would buy. The reranker reads the passage text, so a
flattened table is still a flattened table to it.

The evidence for Docling still has to come from answer quality in F9. F7 does not change
that; it confirms it a second time.

## Latency is still not measured

Median 8,603 ms, and it means nothing again — worse than F6's 4.8 s because the harness now
builds a `CrossEncoder` per call on top of a `SentenceTransformer` per call, then runs 50
pairs through a cross-encoder on a laptop CPU.

What this run genuinely cannot tell us: **whether the `cpu` profile can afford to rerank 50
candidates on an interactive request.** That needs the VPS, a warm TEI, and a measurement of
its own. Until then `rerank_candidates=50` for `cpu` is an assumption, not a finding, and it
is the single most likely number in the profile table to be wrong.

## Reproducing

```
uv run python -m eval.production                      # without the reranker
ZENITH_EVAL_RERANK=1 uv run python -m eval.production # with it
```

Both embed and rerank through PyTorch. TEI publishes `linux/amd64` only — `docker compose up
tei-rerank` on Apple Silicon fails with *"no matching manifest for linux/arm64/v8"* — and the
weights are identical, so the ranking is identical. That is M0's split, unchanged: quality on
the laptop, resources on the machine a customer would use.
