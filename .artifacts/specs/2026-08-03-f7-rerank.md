# F7 — Reranking, and the fusion bug it exposes

Two problems, one feature, and they are related more closely than they look.

**The reranker.** Recall@8 is 80%, Recall@50 is 95%. Every miss is already in the candidate
set at a rank between 9 and 50, so the material is there and the order is wrong. A
cross-encoder reads each passage against the question instead of comparing precomputed
vectors, which is exactly the job.

**The fusion bug.** Identifier questions score **0% at rank 8**. Not because the lexical
half fails to find them — it does find them — but because RRF rewards agreement, and an
identifier match is by definition a passage only one half can find.

```
chunk ranked  1st lexically, absent from dense →  1/61        = 0.0164
chunk ranked  5th in both                       →  2/65       = 0.0308   ← wins
```

A passage containing the exact string someone searched for loses to two mediocre agreements.

---

## 1. The fix: the candidate set is the union, not the fused top-50

Today the pipeline is `two lists of 50 → fuse → top-50 → (nothing) → top-8`. Fusion is
doing two different jobs: **choosing candidates** and **ordering results**. It is bad at the
first and only needed for the second.

```
lexical top-50 ─┐
                ├─► union (≤100) ─► reranker ─► top-8
dense   top-50 ─┘         │
                          └─────► RRF ─► top-8      (when the reranker is off)
```

**With a reranker, RRF stops choosing.** The union goes to the cross-encoder, which reads
every candidate and does not care which half proposed it. A passage found by one half is
judged on its content, which is the only thing that should decide.

**Without a reranker** — `low-spec`, or the service being down — RRF still orders, and it
gets one narrow correction: **the top-ranked hit of each half is always included in the
result set.** Not a tuning parameter and not a weight; a floor. If either half is confident
enough to rank something first, it appears. That is the smallest change that fixes the
identifier case without reintroducing the scale-normalisation problem RRF was chosen to
avoid.

Two of six identifier questions are currently missing from the fused top-50 *entirely*.
Those are the ones the union recovers, and no reranker could have helped them.

## 2. The cross-encoder

`BAAI/bge-reranker-v2-m3`, already in `docker-compose.yml` on port 8082, served by the same
TEI image as the embedder. It takes `{query, texts[]}` and returns a score per text.

Every lesson F5 paid for applies unchanged, because it is the same server:

- **Batches are a token budget**, not a count. A rerank pair is a question plus a
  ~1,200-character passage, so the budget is consumed faster than during ingestion — the
  same `max_batch_tokens` from the profile, with the question counted once per pair.
- **No `--max-concurrent-requests`.** F5 measured that flag killing this image after three
  sequential requests. The reranker container inherits the same command.
- **Sequential requests**, and now on the interactive path, so `attempts=1` and a short
  timeout, as `embed_query` already does.

## 3. Degradation, in three layers rather than one

The reranker is the first component that is genuinely optional, so failure has to be
graceful in a way nothing before it did.

| Situation | Behaviour |
|---|---|
| Reranker off (`low-spec`) | RRF ordering, `degraded: false` — this is the configured product |
| Reranker configured but unreachable | RRF ordering, **`degraded: true`** with a reason |
| Embedder unreachable | lexical only, `degraded: true` (already built) |
| Both unreachable | lexical only, ordered by `ts_rank_cd`, `degraded: true` |

The distinction between rows one and two is deliberate. A customer who chose `low-spec`
knows the reranker is off and `zenith diagnose` names it; a customer whose reranker crashed
does not, and the response has to say so.

## 4. Profile

`rerank_candidates` joins the profile table:

| | `gpu` | `cpu` | `low-spec` |
|---|---|---|---|
| Reranker | on | on | **off** |
| Candidates reranked | 100 | 50 | — |

The cost is real: 50 cross-encoder pairs is 50 passages of forward pass, which on four CPU
cores is not free, and it sits on the interactive path. `cpu` reranks half the union rather
than all of it — the fused order decides which half, and that is the one job RRF keeps.

## 5. What "done" means

1. `make check` green.
2. `python -m eval.production` reports **Recall@8 ≥ 90%** with the reranker on. The ceiling
   is 95%; a reranker that cannot close two-thirds of a 15-point gap is not earning its
   latency.
3. **Identifier questions recover.** They are excluded from the headline, which is precisely
   why they need their own line: the fix is aimed at them and the headline would hide it.
4. Isolation is unchanged. The reranker sees passage text that RLS already released; it
   cannot widen anything, and a test asserts the candidate set is still tenant-scoped.

## 6. Recorded as out of scope

- **Query latency on real hardware.** Still unmeasured, now with a cross-encoder added to
  the path. It needs the VPS and a warm TEI, and it is the number that decides whether `cpu`
  can rerank 50 candidates at all.
- **Label-filtered HNSW.** The eval corpus sits under one label, so nothing here measures
  what happens to recall or speed for a user who reaches a tenth of the corpus.
- **Docling.** M0 deferred its justification to F9. The reranker is the first component that
  reads a table rather than matching it, so F7 is where that evidence becomes *possible* —
  not where it gets collected.
