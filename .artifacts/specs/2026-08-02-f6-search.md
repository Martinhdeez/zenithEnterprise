# F6 — Hybrid search

The first feature a customer can *see*. Everything before it built the conditions for one
query to return the right eight passages, and M0 already measured what that query is worth
before it exists: **Recall@8 75%, Recall@50 95%**, no reranker, on 13 documents and 6,317
chunks.

That number is the acceptance criterion. F6 is not finished when search returns results; it
is finished when it returns *those* results.

---

## 1. The shape

```
question
   │
   ├── lexical: to_tsvector / to_tsquery ──► top 50
   │
   └── dense:   pgvector HNSW ─────────────► top 50
                     │
                     ▼
           Reciprocal Rank Fusion            k = 60
                     │
                     ▼
                  top 50 ──► (F7 reranker) ──► top 8
```

**RRF rather than normalised scores.** `ts_rank` and cosine distance live on different,
corpus-dependent scales. Normalising them is fragile and needs recalibrating whenever the
data changes; RRF uses positions only and has one parameter, which the literature and M0
both leave at 60.

```
score(chunk) = Σ 1 / (60 + rank_in_that_list)
```

**The reranker is F7, not F6.** M0 measured the gap it has to close — misses sit at ranks
9–50, so the target is +20 points against a 95% ceiling — and mixing the two into one
feature would leave us unable to say which half moved the number.

## 2. Isolation is not this feature's job, and that is the point

**No `WHERE tenant_id` in any query F6 writes.** Both halves run inside `tenant_session`,
and the policies on `chunks` and `chunk_embeddings` do the filtering. This is the same
argument as everywhere else in the system: a filter in application code is correct until
someone writes the query that forgets it, and the query that forgets it looks exactly like
the query that does not.

Three specific traps this feature can walk into:

1. **The vector index and the policy must not fight.** `chunk_embeddings` carries a
   denormalised `tenant_id` precisely so the RLS predicate is an equality rather than a
   subquery against `chunks` — a per-row `EXISTS` on the hot path is paid on every query.
2. **Label filtering is on `chunks.label_ids`,** maintained by the F3 triggers. F6 reads it
   and never writes it.
3. **A count is a disclosure.** "No results" and "results you cannot see" must be the same
   response. F6 returns what RLS allows and never reports a total, for the same reason the
   document listing does not.

**The test that matters** is not that search works. It is that tenant A searching for text
that exists only in tenant B's corpus gets nothing — run through A's real session, against
real policies.

## 3. The lexical half, and the bug that has already been paid for

`chunks.tsv` is a generated column: `to_tsvector('english', text)`. The query side **must**
use the same analyser, and `app/features/retrieval/lexical.py` already does, with four
identifiers as regression tests.

This is not a stylistic point. M0's first implementation tokenised queries with
`re.findall(r"[A-Za-z0-9']+", ...)`, which split `119/33` into `119` and `1545-0074` into
`1545` + `0074` while the index held both whole. Lexical search found **one identifier in
six** and looked worthless; fixed, it found four, **two of which dense retrieval cannot find
at all**. The hybrid architecture rests on those two.

Ranking uses `ts_rank_cd`, which accounts for term proximity — for identifier queries the
match is usually exact anyway, and for prose the proximity term is what separates a passage
about the subject from a passage that mentions it.

**On `pg_search`/BM25.** ParadeDB is in the image and its BM25 index is better than
`ts_rank` at scale. F6 ships with `to_tsvector` because it needs no new index, no new
migration, and it is what M0 measured. Moving to `pg_search` is a swap behind the same
function, and it belongs after there is a number to beat.

## 4. The dense half

`chunk_embeddings` with an HNSW index, `vector_cosine_ops`, `m=16`, `ef_construction=64` —
already in migration `0001`.

Two operational details that decide whether this works in production:

- **`ef_search` is a per-session knob.** Left at the default, recall from the index itself
  caps below what the data supports. It is set inside the search transaction, and the value
  belongs in the hardware profile: it is a speed/recall trade, which is exactly what a
  profile is for.
- **Only the active embedding space is queried.** `embedding_spaces` exists so several can
  coexist during a reindex (RNF-08). A query that forgets the filter mixes vectors from two
  models, which are not comparable, and returns confident nonsense.

The question is embedded by the same `TeiClient` F5 built, so the profile's batching rules
apply. A query is one short text, so this is a single request — but it is on the
**interactive** path, unlike ingestion, and that difference is the subject of the one
decision I want to flag.

## 5. The decision I am taking, and its cost

**Query embedding is synchronous and in-request.** On `low-spec` that means the user waits
for TEI, sequentially, behind whatever ingestion is doing — and F5 measured ingestion
holding TEI for **13.4 minutes per 100 pages** on dense text.

That is a real problem, and the MVP answer is to make it visible rather than to solve it:

- Search sets a **short client timeout** on the embedding call and returns a lexical-only
  result with `degraded: true` if it expires. Half a hybrid search now beats a whole one in
  forty seconds, and the response says which one the caller got.
- `mvp.md` §2.12's queue priority — queries take precedence, ingestion yields — is a
  **scheduling change in the worker**, not something the search path can fix. Recorded as
  F6's most likely follow-up.

The alternative, a second TEI instance for queries, doubles the memory footprint on a
profile defined by not having any. Rejected for the MVP.

## 6. The endpoint

```
GET /search?q=...&limit=8&labels=<uuid>,<uuid>
```

- **`query.execute` permission**, which the `member` system role already holds.
- **Results carry the citation payload F7 needs**: chunk id, document id, filename, page
  number, bounding boxes, and the three scores (lexical rank, dense rank, fused). Cheap
  now, and it is what makes a bad answer debuggable six months from now — the same argument
  that put four score columns in `query_citations`.
- **`labels` narrows, never widens.** A caller may filter down to a subset of what they
  reach; supplying a label they do not hold is a 403, not an empty result, because the
  request is nonsense rather than unlucky.
- **The query is logged to `queries`** with retrieval latency. That table exists for
  observability now and the audit trail in iteration 4.

## 7. What "done" means

1. `make check` green, with search tests against real Postgres.
2. Cross-tenant and cross-label isolation proven through real sessions, including that a
   count cannot infer existence.
3. The M0 harness runs against the **real** search path — `eval/pipeline.py` currently has
   its own copy of the fusion logic, written for the tracer bullet. F6 replaces it, and the
   headline number has to come back **at or above 75%**.

That third item is the real acceptance test. Until the harness runs through production
code, the 75% describes a prototype nobody ships.
