# F14 — Hardening, from an audit rather than a wish list

The codebase has no `TODO`, `FIXME` or `HACK` anywhere in `app/` or `src/`. That is not a
sign there is nothing left; it means the remaining gaps were written down in specs instead
of buried in comments. This is what the audit actually found, ordered by what it would cost
a customer.

---

## 1. `/query` has no rate limit, and it is now the most expensive endpoint in the product

`mvp.md` §2.12 specifies the limits and they were deferred to M4 every time they came up:

| Limit | Value |
|---|---|
| Queries per minute per user | 30 |
| Queries per minute per tenant | 120 |

Three things have changed since that deferral, and together they make it the top of the
list rather than the bottom.

**Generation is expensive in a way search never was.** F9 measured ~9 seconds of model time
per answer. F11 measured the box: four cores, and ten concurrent *searches* already take it
to 5.2 seconds each. Ten concurrent generations do not degrade the service, they remove it.

**Streaming holds the connection open for the whole answer.** `POST /query/stream` keeps a
worker and a connection busy for ten seconds or more. Without a limit, thirty tabs left
open on a dashboard that retries is an outage, and nobody involved was being malicious.

**The defence already exists and is used elsewhere.** `SlidingWindowLimiter` was written
for login, for the same reason in a different costume — argon2 is deliberately expensive,
so an unauthenticated flood was a denial of service we had written ourselves. Generation is
the same shape: expensive by design, triggered by a cheap request.

### What ships

- **Two windows, not one.** Per user (30/min) stops one person's runaway tab. Per tenant
  (120/min) stops twenty people's, which the per-user limit cannot see. They fail
  differently, so both are needed — exactly the argument `throttle.py` makes for pairing a
  rate limit with a semaphore.
- **`429` with `Retry-After`**, as §2.12 requires. A client that is told when to come back
  can obey; one that is only told "no" retries immediately and makes it worse.
- **Applied to `/query` and `/query/stream`, not to `/search`.** Search costs ~1.2 s of
  mostly-Postgres and is not what falls over. Rate-limiting it would restrict the cheap
  path to protect the expensive one.
- **Per process, and written down as such.** With several uvicorn workers the effective
  limit is multiplied by the worker count. That is honest for a single-node install and is
  the same trade `throttle.py` already documents; a shared limiter needs Redis and belongs
  with the decision to run more than one node.

## 2. A build artifact reached `main`

`frontend/tsconfig.tsbuildinfo` — TypeScript's incremental cache, machine-specific,
regenerated on every build. It arrived because `tsc -b` writes it beside the config and the
frontend's `.gitignore` was written before the first build ran.

Untracked and ignored. Small, but this is the second time a generated file has reached a
branch in this project (F4's `.html` and `.pdf`), and the pattern is always the same: the
ignore file is written before the tool that generates the artifact is first run.

## 3. Deliberately not done, with reasons

**A shared rate limiter.** Needs Redis or a Postgres table on the hot path. The per-process
version is correct for the single-node install this product ships as, and adding a
dependency for a multi-node deployment nobody has yet is the definition of premature.

**`httpOnly` cookie auth.** The client keeps its token in `sessionStorage`, which is
readable by any script that gets injected. A cookie would be better and needs CSRF
protection, a refresh flow and a decision about cross-origin development — a milestone, not
a hardening item, and recorded in `App.tsx` rather than quietly treated as sufficient.

**Caching the `llm_config` lookup.** `AnswerService._resolve()` reads one row per request.
It is an indexed primary-key lookup on a table with one row per tenant, inside a
transaction the request already needs — call it a microsecond against nine seconds of
generation. Caching it would introduce a staleness window on a configuration change for no
measurable gain.

**Docling.** F9's verdict stands: pdfplumber loses zero of five table anchors on this
corpus. The next step is a harder corpus, not an install.

## 4. What "done" means

1. `make check` green across both suites.
2. A user exceeding 30 queries in a minute gets `429` with `Retry-After`, asserted.
3. A tenant exceeding 120 gets the same, asserted independently of the per-user limit.
4. `/search` is unaffected, asserted — the cheap path stays cheap.
5. No build artifact is tracked.
