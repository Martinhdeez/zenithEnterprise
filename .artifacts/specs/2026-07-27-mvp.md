## 1. Framing

### 1.1 What the MVP is for

**The MVP is not for selling over the web: it is for installing at 2-3 design partners.**

In enterprise B2B, the first real product is installed by hand at pilot customers, free or nearly so. That decision removes, in one stroke: self-service signup, billing, plan management, automated onboarding and most account management. Those are months of work that validate nothing about the product.

### 1.2 Iteration 0 folds in here

The original plan included a separate iteration 0 as a throwaway spike. **It has been removed.**

The hackathon project already validated the idea and the stack. What it did not validate is measured retrieval quality — no Recall@50, no hybrid search, no verified page-level citations. That measurement is still mandatory, but it does not need a phase of its own: the pipeline is built first (M0), it is measured, and the UI only goes on top once the gates pass.

**The evaluation harness stays in the repository permanently**, as a regression test, not as disposable code.

### 1.3 Starting point: a new repository

**We start a new repository.** The hackathon project is consulted as reference, not inherited.

The reason is not code quality. It is that **the database schema is the most structural decision in the project**, and the MVP needs multi-tenancy, Row-Level Security and multiple vector spaces from the very first migration. Retrofitting all of that onto a schema born single-tenant and single-vector is more work and more risk than starting clean. A prototype's Alembic migrations drag along decisions that stay invisible until they break.

What does carry over:

| Item | How |
|---|---|
| React components that work | Port them |
| Docker Compose configuration | As reference |
| General structure and conventions | As reference |
| Knowledge of what caused trouble | The most valuable part |
| Schema, migrations, RAG core | **Not inherited** |

## 2. MVP scope

### 2.1 Roles and permissions (RBAC)

**The administrator creates whatever roles they need, with whatever names and whatever combination of permissions they want.** No hard-coded fixed roles.

**Important nuance: the permission catalogue is defined by the software, not by the customer.** Each permission maps to something the code knows how to check; a permission invented by an administrator would have nothing enforcing it. The administrator composes roles out of the list; they do not extend the list.

MVP catalogue:

```
documents.upload          documents.delete.own      documents.delete.any
query.execute             query.history.own         query.history.any
users.invite              users.manage              roles.manage
labels.manage             llm_config.manage
```

Two system roles, `admin` and `member`, are seeded and marked `is_system` so they cannot be deleted. This protects against the classic mistake: an administrator deletes the last role holding administration permissions and locks everyone out.

**Permission checks read from the database from the first commit**, never comparing against an enum in code. That is what makes adding custom roles configuration rather than a deployment.

### 2.2 Document scope per role (RF-04.2)

Each role bounds which documents it reaches. An employee gets an account with the role matching their function, and that determines what they can see and ask about.

**Model: access labels.** A document carries one or more labels; a role reaches a set of labels.

```
"Finance"   →  Accounting role, Leadership role
"HR"        →  People role, Leadership role
"General"   →  every role
```

**Deliberately not done:** per-document permissions or hierarchical folder inheritance. They are complexity multipliers that cover nothing labels do not already cover, and they turn debugging "why can't this user see this?" into a nightmare.

**Document uploaded without a label:** the uploader must choose a label at upload time, with a default configurable by the tenant administrator. This forces the decision without blocking the flow. Denying by default would make the product look broken; allowing everything by default turns an oversight into a leak.

**Non-inference requirement.** If a user cannot reach a document, it is not enough that they get no answers based on it: **they must also be unable to deduce that it exists**. Not through citations, not through listings, not through messages of the "I found something but you can't see it" kind.

> **Why this enters the MVP rather than iteration 4, as originally planned.** A design partner uploads their real corpus from day one, and inside it there is payroll, board minutes and personnel files. A system where every employee sees everything does not survive the start of the pilot. The original plan assumed a pilot with a narrow document set, and that is not realistic.

### 2.4 Authentication and provisioning

- Email + password, **invitation only**. No open signup.
- The tenant is created during installation, via the CLI (see below).
- Session with a short-lived JWT plus a refresh token.

#### Cold start: how the first user is born

With no open signup, a freshly installed system has no user able to invite anyone. That initial provisioning **cannot be a manual `INSERT` in `psql`**: it is error-prone, it leaves the password hash in the shell history, and it is not deliverable to an on-premise customer.

It is solved with a **CLI in the backend itself**, reusing the application's service layer instead of writing SQL in parallel:

```
zenith create-tenant "Company Name" --admin-email admin@company.com
zenith invite --tenant <slug> --email person@company.com --role "Role name"
zenith reset-password --email admin@company.com
zenith list-tenants
```

Rules:

- The password is **never passed as an argument** — it is generated and printed once, or read from `stdin`. An argument ends up in the shell history and in the process table.
- `create-tenant` also creates the initial system role with the full permission catalogue from §2.1, marked `is_system`. Without it, the administrator is born unable to administer anything.
- The CLI is **the only path** allowed to bypass invitations. Everything else goes through the API.
- `reset-password` exists from the start: there is no outbound mail configured on-premise, and without it the first administrator who forgets their password leaves the installation inaccessible.

It lands in **M3**, alongside users and roles. Until then, M0-M2 use a development seed script that the CLI will eventually replace.

#### Session revocation without Redis

Redis has been excluded from the architecture, so how sessions are invalidated without wrecking latency has to be documented.

**A precision about the problem.** It is sometimes framed as "we will have to check the blacklist on every API request". That is not the case, because there are two tokens with different lifecycles:

| Token | Lifetime | Database check |
|---|---|---|
| Access | 10-15 min | **Never.** It is stateless by design |
| Refresh | Days | Only on refresh: once every 10-15 min per user |

Default revocation latency is therefore the lifetime of the access token. For ordinary sign-out that is acceptable and is the standard trade-off.

**For immediate revocation** (user removed, credentials compromised) something more is needed, and it comes almost free from what is already in place:

- `users.token_version`, an integer incremented on revocation.
- Every API process keeps the set of revoked versions in memory.
- **Postgres pushes changes via `LISTEN` / `NOTIFY`**, the same mechanism `procrastinate` already uses.

Result: an in-memory check per request, zero additional queries, propagation in milliseconds, no Redis and no new services.

**Warning:** SSO (SAML/OIDC) will be the first thing any mid-sized company asks for. It is not in the MVP, but the user model must allow identity to be decoupled from the password, to avoid rewriting it later.

### 2.5 Ingestion

- **PDF only.**
- Multi-file drag-and-drop upload.
- 100 MB limit per file.
- SHA-256 deduplication before processing.
- **Mandatory access-label assignment at upload** (§2.2).

**Warning:** no company uploads documents one at a time; they have folders with thousands. The first request from any customer will be *"can it read our SharePoint or network drive directly?"*. Connectors are iteration 3, but it is worth assuming manual upload is a temporary patch.

### 2.6 Processing visibility

**Not optional.** With an async queue and Docling, a document can take minutes. If the user uploads and sees nothing, they assume it is broken and upload again.

```
queued → processing (page X of Y) → ready
                                  ↘ failed: <readable reason>
```

The failure reason in human language, never a stack trace. It requires the error taxonomy from technical decisions §12.6.

### 2.7 Document management

- Listing with name, date, status, size, page count, labels.
- Filtering by name, status and label.
- Label reassignment.
- Deletion.

The listing respects document scope: a user only sees documents their role reaches.

**Deletion is the delicate part:** deleting a document must delete its pages, chunks and vectors in the same transaction. It is the minimum GDPR demands, and it comes free with `ON DELETE CASCADE`.

#### Physical delete, and why: an accepted risk

The MVP performs **immediate physical deletion**. There is no trash bin and no `deleted_at`.

Both sides of this are real and opposed: physical deletion is what makes complying with a GDPR "delete my data" request trivial, and it is also what turns one mistaken administrator click into irreversible loss of an entire contract corpus.

Physical delete is accepted because `deleted_at` is not free: it forces filtering on **every** read path, and those paths already carry tenant and label RLS. A forgotten filter in a system isolated by RLS does not produce a ghost document in a listing — it produces deleted content appearing inside an answer, with a citation. The cost of getting it wrong is greater than the problem it solves.

Mitigations required in exchange, inside MVP scope:

- **Explicit confirmation by typing the document name**, not a yes/no dialog.
- **No bulk delete in the UI.** One at a time. Batch deletion, if it ever arrives, will be a CLI operation with its own confirmation.
- **Requires the `documents.delete.any` permission**, which is distinct from `documents.delete.own` and not granted by default.
- **Deletion is logged** (who, what, when) in the structured log, which outlives the document.
- The **M5 runbook documents restoring from a Postgres backup** as the only recovery path, with its data-loss window.

> **Accepted and recorded risk.** An administrator with the permission can destroy content irreversibly, recoverable only from a backup. Soft delete with a 30-day purge is the right medium-term answer and is noted for iteration 3, when document management grows and the extra filter can be designed alongside the rest instead of bolted on afterwards.

### 2.8 Querying and answering

**Simple question-answering, no conversational memory.** A visible history of past questions, but each question is independent.

> **Scope trap.** Conversational RAG requires query rewriting: turning *"and the second one?"* into a standalone question before searching. It is a complete subsystem with its own failure modes, and it degrades retrieval when it fails. It gets added once the base case works well, not before.

Answers are **streamed**, because it completely changes perceived latency.

### 2.9 Citations — the differentiator

This is where the customer decides whether they believe the product. It deserves investment disproportionate to its size.

**A citation is not plain text like "page 34".** Clicking it opens the PDF **on that page, with the chunk highlighted**.

The difference between reading "page 34" and seeing the paragraph underlined in the original document is the difference between a sceptical customer and a convinced one.

#### How the highlight works: coordinates, not character offsets

> **Risk defused.** The first version of this document highlighted using `char_start` / `char_end`. **That approach is fragile and must be discarded.** Extracted text normalises whitespace, line breaks, ligatures and hyphenation, while the text layer pdf.js overlays has its own span structure. Character offsets do not correspond between the two, and the highlight comes out misaligned. It is a well-known historical problem with browser PDF viewers.

**We store the bounding boxes that pdfplumber and Docling already produce.** Drawing a semi-transparent rectangle over coordinates is robust; matching text in the DOM is not.

Three implementation details:

- **A chunk is not one rectangle, it is a list.** It spans several lines and can cross pages. An array of boxes is stored, each with its page.
- **Normalised coordinates** relative to page size (0-1), not absolute points, so the highlight survives zoom and any viewer scaling.
- **`char_start` / `char_end` are kept anyway**, but for text operations (showing the excerpt, debugging), never for positioning the highlight.

### 2.10 Abstention and errors

When the system finds no answer it says so explicitly and shows which documents it consulted. Never an empty or generic answer.

Tied to the 0% fabrication gate: abstention is a designed experience, not a silent failure.

### 2.11 LLM connector configuration

Admin screen: endpoint URL, key and model name. Key encrypted at rest.

**A "test connection" button that runs the certification suite (RNF-06)** and shows the result. It is the product's defence: if the customer plugs in a model that fails, they see it right then, instead of it surfacing three months later as a complaint.

### 2.12 Explicit limits

Not for scalability, but to stop one user from taking down the shared GPU. Values fixed for iteration 1, all configurable by environment variable:

| Limit | Value | Reason |
|---|---|---|
| File size | 100 MB | A larger PDF is almost always an uncompressed scan; parsing cost explodes |
| Documents per tenant | 5,000 | Generous for a design partner; bounds the HNSW index to a size measured in M0 |
| Pages per document | 3,000 | One document cannot monopolise the queue |
| Queries per minute per user | 30 | Intensive human use fits comfortably; accidental scripting does not |
| Queries per minute per tenant | 120 | Aggregate ceiling, protects the GPU against several concurrent users |
| Concurrent ingestions per tenant | 1 | Queue fairness, §3.6 |

Query limits are enforced in FastAPI middleware with a sliding window over Postgres, returning `429` with `Retry-After`. Storage limits are checked at upload and return `413` or `409` with the reason.

> **These numbers are an initial position, not a measured result.** They are revisited at the close of M0, when real retrieval latency over the full corpus exists. What is not negotiable is that they are implemented and tested in M4: a limit that is written down but not enforced protects nothing.

### 2.13 Observability

Structured log of every query: tenant, user, question, retrieved chunks **with their scores at each phase**, latency per phase, model used.

It serves simultaneously to debug retrieval quality with real data and as the seed of the query audit trail (iteration 4). One piece of work, two requirements.

### 2.14 Explicit non-goals

Writing them down avoids arguments three months from now:

Audio and transcription · Spanish and other languages · Auto-categorisation · Faceted navigation · Per-document permissions · Folder hierarchies · SSO · External connectors (SharePoint, Drive) · Conversational memory · Mobile app · Billing · Self-service signup · Public API · High availability · Kubernetes

**On audio — closed decision.** It stays out of the MVP. The core of the product is that hybrid search and data isolation work perfectly: if RAG over PDF fails, audio is irrelevant. Value is demonstrated to the design partner with English PDFs, and audio enters in iteration 2. It is no longer an open question.

## 3. Architecture

### 3.1 Components

```
┌─────────────────┐
│  React + Vite   │  Browser
└────────┬────────┘
         │ HTTP / SSE
┌────────▼────────┐
│    FastAPI      │  API: auth, upload, query, admin
└────────┬────────┘
         │
    ┌────┴─────────────────────┬──────────────────┐
    │                          │                  │
┌───▼──────────┐      ┌────────▼───────┐   ┌──────▼─────────┐
│  PostgreSQL  │      │      TEI       │   │ Pluggable LLM  │
│              │      │                │   │                │
│ · pgvector   │      │ · BGE-M3       │   │ · Ollama/vLLM  │
│ · pg_search  │      │ · reranker-v2  │   │ · Azure/cloud  │
│ · queue      │      └────────▲───────┘   └──────▲─────────┘
│ · RLS        │               │                  │
└───▲──────────┘               │                  │
    │                          │                  │
┌───┴──────────────────────────┴──────────────────┘
│   Worker (same code base, different entrypoint)
│   · ingestion: parsing, chunking, embeddings
│   · background reindexing
│   · idempotent retries
└──────────────────────────────────────────────────
```

Four containers: `api`, `worker`, `db`, `tei`. The LLM is external and supplied by the customer.

### 3.2 Ingestion flow

```
Upload → magic-byte verification → SHA-256 hash → duplicate? → yes: reject
                                                       │ no
                                                       ▼
                                            Enqueue job (Postgres)
                                                       │
                                                       ▼  [worker]
                            Per-page analysis: text layer? tables?
                                                       │
                                  ┌────────────────────┴──────────┐
                                  ▼                               ▼
                             pdfplumber                       Docling
                            (simple text)              (tables / scanned)
                                  └───────────────┬───────────────┘
                                                  ▼
                        Structural chunking (500-800 tokens, 15% overlap)
                                                  ▼
                        Contextual enrichment (cheap local LLM)
                                                  ▼
                        Embeddings via TEI → active vector space
                        + tsvector for lexical search
                                                  ▼
                        Transactional insert  →  status: ready
```

The entire worker block happens in **one transaction per document**: if it fails halfway, it rolls back together with the queue state. That is where RNF-05 comes from with no extra code.

### 3.3 Query flow

```
Question
   │
   ├──► BM25 / pg_search ────► top 50   (tenant-filtered via RLS)
   │
   └──► pgvector, active space ─► top 50   (tenant-filtered via RLS)
                │
                ▼
        RRF  (k = 60)  ──────► combined top 50
                │
                ▼
        TEI re-ranker ───────► top 8
                │
                ▼
        Pluggable LLM (streaming) + citations with offsets
                │
                ▼
        Structured log: chunks and scores from every phase
```

### 3.4 Isolation and scope: Row-Level Security

Two levels of filtering, both guaranteed by **Postgres RLS** and not by `WHERE` clauses in application code. Detail and rationale in technical decisions §5.

| Level | Requirement | Policy |
|---|---|---|
| Between tenants | RF-04.1 | The session's `tenant_id` |
| Between roles inside a tenant | RF-04.2 | Labels reachable by the user's role |

With RLS, a query that forgets the filter does not return someone else's data: the database rejects it. Isolation stops depending on team discipline.

**A technical risk the second level introduces.** Filtering inside a vector search degrades the HNSW index: if a user reaches only 5% of the corpus, the index walks much further to gather 50 candidates and Recall may drop relative to the unfiltered measurement. This is a known pgvector problem.

It is handled by **turning it into a measurement in M0** (§7), not by discovering it in production. If Recall holds, Postgres stays with the decision validated by data. If it collapses, there is a measured justification for introducing Qdrant — in week four with an empty database, not with three customers in production.

### 3.5 Hot reindexing

The schema allows several vector spaces to coexist (technical decisions §4). Even though only one is active in the MVP, **the capability is built from the first migration**: retrofitting it with customers in production means migrating the schema, rewriting the retrieval layer and coordinating maintenance windows.

Doing it now, with an empty database, is one more table and on the order of 200 lines.

### 3.6 VRAM management and queue fairness

Explicit bounds: one heavy job at a time, TEI with a fixed batch size, and queries taking priority over ingestion and reindexing.

**The noisy-neighbour problem.** With a strict FIFO queue, if one tenant uploads 50 scanned contracts at once, another tenant who then uploads a two-page document waits hours watching "processing" while the GPU is busy.

**Mitigation: a per-tenant concurrency cap.** At most one job in flight per tenant, so a bulk load is processed serially and leaves room for everyone else immediately. It is simpler than full round-robin and solves the same problem.

**A detail that matters:** the scarce resource is not the queue, it is the GPU. There is already a semaphore allowing one heavy job at a time, so fairness must be applied **at GPU admission**, not only when dequeuing. Otherwise the per-tenant cap is honoured at dequeue and lost immediately afterwards.

*Scope: the noisy neighbour only exists in hosted mode. In an on-premise deployment there is one tenant per installation and the problem reduces to fairness between users of the same customer. Since the initial deployment mode is still open (§9) and the cap is cheap, it is implemented anyway.*

### 3.7 Connection pool separation

Postgres concentrates relational storage, vectors, lexical search, RLS and the queue. That requires isolating workloads so an ingestion spike does not degrade real-time searches.

**Two separate pools in FastAPI:** one for user reads (search), another for ingestion and reindexing workers. It stops a burst of writes from exhausting the connections available for querying.

**Correcting a common diagnosis:** the load is often attributed to workers *polling* the queue continuously. `procrastinate` does not poll: it uses Postgres `LISTEN` / `NOTIFY`, so workers wait for a notification instead of asking in a loop. The I/O pressure from that side is far smaller than it appears.

**The real contention** is elsewhere and has to be addressed there:

- HNSW search is CPU-heavy. A separate pool avoids running out of connections, but it does not avoid competing for CPU.
- Bulk ingestion inserts large volumes of chunks and vectors, generating write and `VACUUM` pressure.
- Concrete mitigations: `statement_timeout` on the search path so no query hogs resources, tuning `maintenance_work_mem` for HNSW index builds, and building indexes outside the ingestion peak.
- If CPU contention persists at real scale, the way out is a read replica for search. **Out of MVP scope**, but pool separation leaves it ready.

## 4. Data model

The most expensive part to get wrong. It is fixed in full from the first migration.

```
tenants
  id, name, created_at

users
  id, tenant_id, email, password_hash, token_version, created_at
  UNIQUE (tenant_id, email)

permissions                                ← closed catalogue, defined by the software
  code, description

roles                                      ← created by the tenant administrator
  id, tenant_id, name, is_system

role_permissions
  role_id, permission_code

user_roles
  user_id, role_id

access_labels                              ← RF-04.2
  id, tenant_id, name

document_labels
  document_id, label_id

role_labels                                ← which labels each role reaches
  role_id, label_id

documents
  id, tenant_id, filename, sha256, status, status_detail,
  label_ids,                               ← copy of document_labels, see below
  page_count, size_bytes, uploaded_by, created_at
  UNIQUE (tenant_id, sha256)              ← deduplication RF-03.3

pages
  id, document_id, page_num, extraction_method, text
  ON DELETE CASCADE                        ← allows reindexing without re-parsing

chunks
  id, document_id, tenant_id, label_ids, page_num,
  char_start, char_end,                    ← text only, NOT for highlighting
  bboxes jsonb,                            ← [{page, x0, y0, x1, y1}, ...] normalised 0-1
  section, text, context_prefix,
  chunking_version, tsv tsvector
  ON DELETE CASCADE
  GIN index on tsv and on label_ids

chunk_embeddings                           ← RNF-08
  chunk_id, tenant_id, embedding_model, embedding_version, embedding vector(1024)
  PRIMARY KEY (chunk_id, embedding_model, embedding_version)
  HNSW index on embedding

embedding_spaces                           ← RNF-08
  model, version, dimension, status        -- active | building | retired

queries                                    ← observability + future audit
  id, tenant_id, user_id, question, answer, model_used,
  latency_retrieval_ms, latency_generation_ms, created_at

query_citations
  query_id, chunk_id, rank,
  score_bm25, score_vector, score_rrf, score_rerank

llm_config
  tenant_id, endpoint_url, api_key_encrypted, model_name,
  certified_at, certification_result

ingestion_jobs                             ← managed by procrastinate
```

**Five deliberate details:**

`chunks.tenant_id` and `chunk_embeddings.tenant_id` are **denormalised** (both derivable via `document_id`). They are duplicated on purpose: the tenant filter must apply inside the vector query, and a `JOIN` there penalises the HNSW index. In `chunk_embeddings` there is an additional RLS reason: it is the hot-path table, and a policy using `EXISTS` against `chunks` would be paid per row on every query.

`documents.label_ids` replicates `document_labels` **because of a Postgres constraint, not for performance**. If the RLS policy on `documents` read `document_labels`, and the policy on `document_labels` reads `documents`, the policies call each other and the engine aborts on mutual recursion. With the copy, no policy needs to look at the join table. The cost is keeping both in sync in the same code path.

`chunks.bboxes` is what makes highlighting the chunk in the PDF viewer possible (§2.9). It is extracted during parsing, so adding it later forces a re-parse of the whole corpus — not just a re-embed. It is one of the few fields whose omission genuinely costs days.

`pages.text` and `chunks.text` persist each stage separately. **This is what makes reindexing cost hours instead of days**: already-extracted text is re-embedded without running Docling again.

`query_citations` stores the scores from all four phases. It is what will make it possible, six months from now, to answer why one specific query returned garbage.

### 5.4 Models and inference

| Function | Choice |
|---|---|
| Embedding and re-ranking serving | **TEI** (Apache 2.0) |
| Embeddings | **BAAI/bge-m3** (MIT) |
| Re-ranker | **BAAI/bge-reranker-v2-m3** (MIT) |
| Contextual enrichment | Small local LLM via Ollama |
| Generation | Pluggable, OpenAI-compatible interface |
| **Generation in development and CI** | **Llama 3.1 8B Instruct via Ollama** — fixed baseline |

#### Why a development model has to be fixed

"Pluggable" describes the interface, not the working environment. Writing and tuning citation prompts requires a concrete, stable model: if every developer tests with a different one, no prompt regression is reproducible and the certification suite has nothing to compare against.

**Llama 3.1 8B Instruct** (Llama 3.1 Community licence, permits commercial use below 700M monthly active users; verified in the licence review of §5.3). Equivalent alternative: Mistral 7B Instruct v0.3, Apache 2.0, if the Llama licence makes a customer uncomfortable.

The reasoning is about the **floor, not the ceiling**: an 8B model is among the worst a customer will plug in. If the citation format holds there, any large cloud model meets it effortlessly. The reverse does not work — tuning prompts against GPT-4o produces instructions the 8B breaks, and the failure appears at the first customer deploying locally.

Operational consequences:

- It is the model that runs in **CI**, so citation tests depend on no external API and no credit.
- It is the **base case of the RNF-06 certification suite**: the "≥1 certified local model" gate is covered by it.
- Generating the synthetic evaluation set over real documents runs on this stack, which is what RNF-07 demands.

TEI in its own container instead of in-process `sentence-transformers`: it separates model loading from the API lifecycle, provides batching, and allows moving the GPU to another machine without touching code.

```
├── backend/
│   ├── app/
│   │   ├── main.py
│   │   ├── cli.py                  # create-tenant, invite, reset-password (§2.4)
│   │   ├── core/                   # config, database, logging, security
│   │   ├── common/                 # exceptions, base repository with RLS context
│   │   ├── models.py               # central registry for Alembic — imports only
│   │   └── features/
│   │       ├── tenancy/            # tenants, RLS context
│   │       ├── auth/               # users, roles, permissions, sessions
│   │       ├── labels/             # access_labels, role_labels, document_labels
│   │       ├── documents/          # documents, pages, chunks; listing and deletion
│   │       ├── ingestion/          # jobs, parsers/, chunking/, errors.py
│   │       ├── embeddings/         # chunk_embeddings, embedding_spaces, TEI, reindexing
│   │       ├── retrieval/          # BM25, vector, RRF, re-ranking
│   │       ├── query/              # queries, query_citations, query endpoint
│   │       └── generation/         # prompts, citations, certification
│   │           └── adapters/       # openai_compatible.py
│   ├── alembic/
│   ├── eval/                       # EVALUATION HARNESS — permanent, not disposable
│   │   ├── corpus/
│   │   ├── questions/              # manual core + synthetic set
│   │   └── run.py                  # Recall@50, Recall@8, MRR, citation accuracy
│   └── tests/integration/          # only what crosses features (testcontainers)
├── frontend/
│   └── src/
│       ├── features/               # documents, search, admin
│       ├── core/
│       └── api/                    # client generated from OpenAPI
├── docker/
└── .artifacts/specs/
```

Each feature contains `model.py`, `repository.py`, `router.py`, `schemas.py`, `service.py` and its own `tests/`. **Feature-based organisation, no layer directories**: a real change is almost never "touch every model", it is "change how ingestion works", and it must fit in a single directory.

Three rules that hold the structure together:

- **The model is owned by whoever creates the row.** `chunks` is written by ingestion and read by retrieval; it lives in `documents/` because that is its lifecycle, and `retrieval/` imports it. Without this rule, two definitions of the same table appear.
- **`tests/integration/` still exists at the top.** The cross-tenant and cross-label leak tests belong to no feature: they verify what happens *between* them, and they are two MVP gates.
- **`app/models.py` is an import registry**, not a model package. Alembic needs a single `MetaData` to autogenerate. It is the only concession to layer organisation and it is plumbing.

**The connector is not organised by vendor.** The folder is `generation/`, with `adapters/openai_compatible.py` inside. A folder named `openai/` starts lying the day a customer plugs in Bedrock, and it drags vendor details into the rest of the code.

`eval/` lives inside `backend/` and is part of the product, not part of disposable testing.

## 7. Milestones

### M0 — Foundations, pipeline and harness (~4-5 weeks)

Iteration 0 folded in, plus the engineering layer. **No user interface.**

**Foundations**
- Repository, CI, `ruff`, strict `pyright`, licence checking.
- Full schema from the first migration: multi-tenancy, RLS, vector spaces.
- Cross-tenant leak test, green.

**Pipeline**
- Command-line ingestion: parser routing, chunking, embeddings via TEI.
- Hybrid retrieval with RRF and re-ranking.

**Evaluation harness**

Corpus (~50 documents, English):
- **~40 real public corporate documents.** Annual reports and 10-Ks from SEC EDGAR (financial tables, identifiers, public domain), EU regulations and tenders. Free and unrestricted.
- **~10 synthetic, fabricated on purpose**: contradictions between documents, duplicate versions of the same contract, scanned pages.

> **Why fiction or AI-generated text will not do.** A corpus of clean prose contains no exact identifiers (contract numbers, codes, references like `FAC-2026-99`), which is precisely what justifies the lexical half of hybrid search. Measuring over prose would lead to the conclusion that BM25 adds nothing — true on that corpus, false in production. The same applies to tables, scanned pages and near-duplicates.

Question set, in two tiers:

> **The lexical overlap trap.** If questions are generated from the chunk itself, they reuse its exact vocabulary. Recall comes out artificially high and collapses in production, because real users do not ask using the document's words. The set becomes a mirror instead of a test, and the failure goes undetected until there are customers.

- **Tier 1 — Manual core (20-30).** Hand-written, without looking at the document while formulating them. Reliable ground truth.
- **Tier 2 — Synthetic set (~150).** Generated with an LLM in two passes: generation, and an **adversarial pass** rewriting each question in real employee vocabulary, removing terms copied from the original. Rejection criterion at review: *"does it look too much like the source sentence?"*.
- **Hand-made adversarial cases (10-15).** Questions with no answer in the corpus, and contradictory documents. An LLM generates these badly because it tends to be cooperative.

**RNF-07 constraint and the design partner's corpus.** The corpus must **resemble the design partner's documentation in type and structure** (if one is already identified), but using public equivalents. Using their real documents and generating the synthetic set from them with a cloud model would violate RNF-07. If real customer documents are ever used, question generation must run on the local stack.

**Highlight validation.** Over the manual core of 25 questions, it is verified by hand that the rectangle drawn from `bboxes` lands on the correct text. This is the check that defuses the risk in §2.9, and doing it in M0 avoids discovering in M2 that the highlighting approach does not work.

**Exit gate — the four gates:**

| Metric | Threshold |
|---|---|
| Recall@50 (pre-rerank) | ≥ 95% |
| Recall@8 (post-rerank) | ≥ 90% |
| Citation accuracy (manual, core of 25) | ≥ 95% |
| Fabrication with a false citation | **0%** |

**If they do not pass, no UI gets built on top.**

**Measurements recorded as baselines:** MRR@8, abstention rate, hybrid gain over pure vector, contextual enrichment gain, pages/minute per parsing route, € per 1,000 pages.

**Critical added measurement — filtered retrieval.** Recall@50 and p95 latency with the user reaching **100%, 20% and 5%** of the corpus. This is what decides whether pgvector withstands the RF-04.2 label filtering or whether Qdrant has to be introduced. Finding out here costs a day; finding out with customers in production costs a migration.

### M1 — Production ingestion

Upload via API with magic-byte verification, queue with procrastinate, per-page parser routing, real-time status, deduplication, cascading delete, readable error taxonomy.

### M2 — Querying and citations

## 8. MVP acceptance criteria

| Criterion | Type | Threshold |
|---|---|---|
| Recall@50 / Recall@8 | Gate | M0 baseline, no degradation |
| Citation accuracy | Gate | ≥ 95% |
| Fabrication with a false citation | Gate | **0%** |
| p95 retrieval + fusion + re-ranking | Gate | < 500 ms |
| Cross-tenant data leak | Gate | **0 cases**, automated test |
