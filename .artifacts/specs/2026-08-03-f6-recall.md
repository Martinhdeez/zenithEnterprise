# F6 acceptance — the M0 baseline through production search

M0 measured Recall@8 at 75% with a tracer bullet: its own table, its own chunker, its own
fusion, no RLS. That number described a prototype nobody would install. This is the same
corpus and the same 36 questions run through **`SearchService`** — production parsing,
routing, chunking, the real `chunks` and `chunk_embeddings` tables, real policies, the real
HNSW index.

Reproduce with `uv run python -m eval.production`.

## Result: PASS

| | Tracer bullet (M0) | Production (F6) |
|---|---|---|
| **Recall@8** (factual + cross-document) | 75% | **80%** |
| Recall@50 | 95% | **95%** |
| Document-level Recall@8 | 100% | **100%** |
| Chunks | 6,317 | 6,511 |

The baseline transfers, and it improved by five points. The production chunker is the
plausible cause — it breaks on paragraph and sentence boundaries rather than at a fixed
1,200-character offset, so fewer answers are cut in half. That is a hypothesis, not a
finding: nothing here isolates it.

**Recall@50 is unchanged at 95%**, which matters more than the headline. It is the ceiling
the reranker has to work under, and it did not move — so F7's target is now **+15 points
against the same ceiling**, not +20.

## The identifier result needs stating carefully

**Identifier questions score 0% at rank 8**, and two of them are not found at rank 50
either. That looks alarming next to M0's headline finding that fixing the tokeniser took
the lexical half from 1 of 6 to 4 of 6.

The two numbers are not comparable. M0's figure was a **diagnostic on the lexical half
alone, at rank 50**. This is **fused, at rank 8**. Fusion is exactly what would hurt here:
RRF rewards agreement, and an identifier match is by nature a passage only one half can
find. A chunk ranked first lexically and absent from the dense list scores `1/61`, while a
chunk both halves rank fifth scores `2/65` and beats it.

So the honest reading is: **the hybrid design finds identifiers, and the fusion buries
them.** That is a ranking problem in RRF's treatment of single-half hits, not evidence
against the lexical index.

It is recorded as **F7's first question**, not fixed here. Two candidate answers, neither
tested:

1. A reranker sees the identifier in the passage text and lifts it — the cross-encoder is
   built precisely for the case where one signal is decisive.
2. Weight the halves in the fusion, or boost exact-match hits. Cheaper, and it re-introduces
   a tuning parameter that RRF was chosen to avoid.

`identifier` is excluded from the headline by design, and was before this run — the reason
recorded in `eval/questions.py` is that it is a diagnostic on one half rather than a measure
of overall quality. That decision was made before this number existed, which is the only
reason it can be cited now.

## Latency is not measured here

Median 4,834 ms per query, and it means nothing. `LocalEmbedder` constructs a
`SentenceTransformer` on **every call**, so almost all of that is model loading on a laptop.
Production embeds a query through TEI over HTTP.

Query latency needs its own measurement on the VPS, against a warm TEI, and it is not in
this run. Recorded as an open item rather than quietly reported as a number.

## What this run is not

- **Not a test of the ingestion pipeline.** Parsing, routing and chunking are the shipped
  code; the *writing* is direct SQL, because this machine embeds through PyTorch and the
  pipeline embeds through TEI. Swapping that one call is the whole difference.
- **Not a measurement of TEI's ranking.** PyTorch and TEI serve identical BGE-M3 weights, so
  the vectors and therefore the ranking are the same. That is M0's split: quality on the
  laptop, resources on the machine a customer would use.
- **Not run under label restriction.** The whole corpus sits under one label. The cost of
  filtering an HNSW search by label is a separate question, still unmeasured, and it is the
  one that decides whether search stays fast for a user who reaches a tenth of the corpus.
