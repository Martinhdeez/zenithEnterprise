# F2 — Authentication and permissions

**Date:** 2026-08-02
**Status:** planned
**Milestone:** M3
**Branch:** `feat/f2-auth`
**Specification:** `.artifacts/specs/2026-07-27-mvp.md` §2.1, §2.4
**Depends on:** F1 — `TenantContext`, `tenant_session`, `owner_session`

---

## 1. Goal

Answer two questions the system currently cannot: **who is this**, and **may they do this**.

F1 delivered the scoping mechanism but nothing that produces a context from a real request. F2 closes that loop: a login returns a token, a token resolves to a `TenantContext`, and every endpoint declares the permission it needs.

**Exit criterion:** a user logs in, calls an endpoint, and is refused when their role lacks the permission — with the refusal enforced by a dependency, not by a check someone remembered to write.

---

## 2. Scope

### 2.1 Permission catalogue

The catalogue is defined by the software and seeded by a migration, not created by customers (mvp.md §2.1). A permission the code cannot check would be a lie in the UI.

```
documents.upload          documents.delete.own      documents.delete.any
query.execute             query.history.own         query.history.any
users.invite              users.manage              roles.manage
labels.manage             llm_config.manage
```

`permissions` has no `tenant_id` and no RLS: it is a global catalogue, identical in every installation.

**Seeded in migration `0002`**, not at application startup. Startup seeding means the row set depends on which version last booted, which is unversioned state pretending to be schema.

### 2.2 Roles

Created by the tenant administrator with whatever name they choose. Two are seeded per tenant at creation time — `admin` with the full catalogue and `member` with `query.execute` and `query.history.own` — both marked `is_system` so they cannot be deleted.

**The rule worth enforcing in code:** a tenant must never end up with zero users holding `users.manage` and `roles.manage`. This is the classic lockout, and recovering from it on-premise means someone in `psql`.

**There are three routes into it, not two.** The obvious ones are deleting the last such role and stripping the last such assignment. The third is deleting or deactivating the last *user* who holds it: `user_roles` cascades on `users.id`, so the row vanishes silently and the tenant is left with a role nobody has. The guard therefore belongs on the **user** deletion and deactivation paths as well as the role ones — it has to be a check on the resulting state ("would this leave zero?"), never a check on the operation.

**Deferred to M3, deliberately.** F2 ships no user or role management, over HTTP or otherwise, so the guard would have nothing to guard: dead code protecting an operation that does not exist yet. It moves with the endpoints that can trigger it, and the three routes above are the specification for it.

### 2.3 Password handling

`argon2-cffi`, already wired in `core/security.py` from F0. Argon2id, not bcrypt — bcrypt silently truncates at 72 bytes, which turns a long passphrase into a weaker secret than the user believes they chose.

Verification runs on **every** login attempt, including for unknown emails, against a dummy hash. Skipping the hash when the user does not exist makes response time a user-enumeration oracle.

**That decision creates a denial of service, and the two must ship together.** Argon2 is expensive by design; an endpoint that runs one per failed attempt, reachable without credentials, is a way for anyone to exhaust a VPS with a loop of invented addresses. Rate limiting on login is therefore **in F2, not M4**. Two defences, because they fail differently:

- A per-source sliding-window limit (`login_attempts_per_minute`, default 10) caps ordinary flooding.
- A semaphore (`password_hash_concurrency`, default 4) caps how many verifications run at once whatever their source, which is what bounds peak memory when the flood is distributed.

Hashing also runs off the event loop. argon2 is blocking C code: called directly in a coroutine it stalls every other request in the process for its full duration, including the health check the load balancer is watching.

Both defences are per process and reset on restart, so with N workers the effective limit is N times higher. Honest for a single-node install, written down rather than glossed over; a shared limiter belongs with the other §2.12 limits in M4. The limit is keyed on the peer address, which behind a reverse proxy is the proxy — running with `--proxy-headers` and a trusted forwarded-for list is a **deployment requirement**, not an optional flag.

### 2.4 Tokens

Already implemented in F0 (`issue_token` / `decode_token`); F2 puts them to work.

| Token | Lifetime | Database check |
|---|---|---|
| Access | 15 min | **Never** — stateless by design |
| Refresh | 14 days | Only on refresh |

The access token carries `sub`, `tid`, `ver` and `typ`. **`ver` is what makes revocation possible without Redis**: `users.token_version` is bumped, and any token carrying a lower version is dead.

**Immediate revocation is deferred to F2b or M4**, not built here. It needs the `LISTEN`/`NOTIFY` cache described in mvp.md §2.4, and the honest position for the MVP is that default revocation latency is the access token lifetime. Building the cache before there is a logout flow to trigger it is speculative.

What F2 does build: `token_version` is **read on refresh**, so a bumped version invalidates the refresh path immediately even without the cache.

**Known consequence: revocation is per user, not per session.** `token_version` is one integer on the user row, so bumping it kills every session that user holds. Someone signed in on a laptop and a phone who signs out of the phone is signed out of the laptop too. This is **expected behaviour for the MVP**, recorded here so that nobody opens it as a bug in M3. Per-device revocation needs a sessions table with one row per issued refresh token, which is a real feature with its own cleanup job — worth building when there is a reason, not before.

### 2.5 The dependency chain

This is the part that matters architecturally:

```
Authorization: Bearer <token>
        ↓  decode, verify type and expiry
current_user       → User
        ↓  load roles → permissions → labels
current_context    → TenantContext
        ↓
requires("documents.upload")  → 403 or proceed
```

Three properties this must have:

- **Labels come from roles, resolved here.** F1 deliberately left `context_for` returning no labels. F2 fills them in from `role_labels`, and that is the only place the resolution happens.
- **Permissions are read from the database**, never compared against an enum. That is what makes custom roles configuration rather than a deployment (mvp.md §2.1).
- **`requires(...)` is a dependency, not a call inside the handler.** A check written in the body can be forgotten; a missing dependency is visible in the signature and in the OpenAPI schema.

### 2.6 Endpoints

```
POST /auth/login      email + password  → access + refresh
POST /auth/refresh    refresh           → new access
GET  /auth/me         → user, roles, permissions, reachable labels
```

Invitations and user management are **M3**, not F2. F2 delivers the mechanism; the CLI and the admin screens that use it come later.

### 2.7 Out of scope

- Invitation flow and user CRUD over HTTP — M3.
- Immediate revocation cache — deferred, see §2.4.
- Label management as an entity — F3. F2 reads `role_labels`; nothing writes them yet.
- SSO — iteration 4. The user model must not couple identity to the password column, so that adding it later is not a rewrite.
- The anti-lockout guard — M3, with the endpoints that can trigger it. See §2.2.
- A **shared** rate limiter across processes and nodes — M4. The per-process one ships here; see §2.3.

## 3. Data

No new tables — F0's schema already has them all. Migration `0002` seeds `permissions`, adds an index on `users.email` (the existing `UNIQUE (tenant_id, email)` cannot serve a login, which knows the address but not yet the tenant), and creates `zenith_authenticate_lookup`.

**`zenith_authenticate_lookup` is the one `SECURITY DEFINER` object in the schema.** Login has to find a user before a tenant context exists — the context is what the login is establishing — so that query cannot go through RLS. The alternative was an owner session inside an unauthenticated HTTP handler, and the owner connection reads every row in the installation. This function returns four fields for one address and nothing else, with `search_path` pinned so a caller-controlled schema cannot hijack it. Auditing the bypass surface stays one grep.

The `downgrade` deletes the seeded rows, which is only safe because `role_permissions.permission_code` cascades — by the time anyone rolls back, real roles reference those codes, and without the cascade the rollback would abort on a foreign-key violation in the one situation where things are already going wrong. Verified by `test_downgrade_works_with_permissions_already_granted` rather than assumed from reading the DDL.

`role_permissions`, `user_roles` and `role_labels` are read heavily on every request. The permission set for a user is a three-table join; if it shows up in latency measurements it gets cached per access-token lifetime, not before.

## 4. Tests

Feature tests (`app/features/auth/tests/`):

| Test | What it protects |
|---|---|
| Correct password authenticates; wrong one does not | Baseline |
| Unknown email takes comparable time to a wrong password | No user-enumeration oracle |
| Access token cannot be used where a refresh token is expected, and vice versa | `typ` is checked, not assumed |
| Expired token is rejected | |
| Token with a stale `ver` fails on refresh | Revocation works on the path that checks the database |
| Permissions resolve from roles, not from code | |
| A user with two roles gets the union of their permissions and labels | |
| Removing the last `roles.manage` assignment is refused | The lockout |

Integration (`tests/integration/`):

| Test | What it protects |
|---|---|
| `requires(...)` returns 403 without the permission, 200 with it | The dependency actually enforces |
| The context built from a token carries exactly the labels of the user's roles | **The join between F2 and RF-04.2** — if this is wrong, a user sees documents their role does not reach, and RLS will faithfully enforce the wrong answer |
| Two users of different tenants get contexts that cannot see each other | End-to-end version of the F1 guarantee |

**The label-resolution test is the important one.** RLS enforces whatever context it is given. A correct policy fed a wrong context produces a confident, silent leak — which is precisely the failure mode the whole design exists to prevent.

## 5. Risks

| Risk | Mitigation |
|---|---|
| Wrong labels in the context defeat RLS entirely | The resolution test above; label resolution exists in exactly one function |
| Argon2 on an unauthenticated endpoint is a CPU/RAM exhaustion primitive | Per-source rate limit **and** a concurrency cap, both in F2; hashing moved off the event loop |
| The rate limit is per process, so N workers means N times the limit | Accepted and documented for a single-node install; shared limiter in M4 |
| Behind a proxy, every request appears to come from one address | Deployment requirement: `--proxy-headers` with a trusted forwarded-for list |
| Signing out on one device signs out all of them | Accepted MVP behaviour, documented in §2.4 so it is not filed as a bug |
| The last administrator is deleted rather than demoted | The guard covers user deletion too; specified in §2.2, built in M3 |
| Downgrading 0002 aborts on granted permissions | The cascade makes it safe, and a test proves the cascade |
| Permission join cost per request | Measured first, cached only if it appears in latency |
| `permissions` seed drifting from the code | Two copies by necessity, guarded by `test_catalogue_matches_the_database` |
