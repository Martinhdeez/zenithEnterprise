# Score contract diagnosis

The earlier QASPER development study recorded eight `probability_mass` failures in 40 Score batches but retained only failure codes. Those old response bytes cannot be reconstructed. The new run re-created candidate inputs from the pinned public QASPER development JSON; its answers are **new** observations on already-seen cases, not recovery of the historical payloads or a new locked test.

The user approved a capped public/synthetic pilot (320 total calls, 500,000 input tokens, 30,000 output tokens, $3). A first synthetic 16-Score-call pilot was valid throughout. A separate 32-call reprobe of four historical failed batches returned 31 valid responses and one new `probability_mass` failure. New Score validity is 47/48; the historic 8/40 and new 1/32 reprobe rates answer different questions. No normalization or mass-tolerance change was made.

The failing new HTTP response had status 200, reported `jev-1.13.0`, a Score answer with string keys `"0"` through `"5"`, and probabilities `0, .02, .04, .16, .54, .23`; sum `0.99`. Its provider score field was `3.93`, while the displayed distribution's expected zero-based grade is `3.89`. The input SHA-256 is `0e6a0d29102925d11ec04cdd4eb933ed669ba777834f1a995037bd0c17a6a9a5`; case `2004.01853:193ee49ae0f8827a6e67388a10da59e137e7769f:4`. Raw response and complete manifest remain only under ignored `.scratch/evidence-v3-hardening/score-reprobe-v1/`; the manifest SHA-256 is `cc3212bf173c9797ee93db98bfb4244dd3ef86f567d83140c0518e0877299172`.

The opt-in recorder requires `public` or `synthetic` classification and an ignored `.scratch` path. It bounds bytes and stores HTTP status, content type, allowlisted request ID, request/rubric/model hashes, validator diagnostics, and timing before parsing. It omits credentials, headers, and request/source text; normal product mode does not create raw response logs. Regression tests exercise capture, duplicate/missing levels, mass diagnostics, and failures.

The newly observed response falls outside the client's strict mass tolerance as displayed. The official human-readable [HTTP API reference](https://docs.typesafe.ai/api) says the string-keyed level probabilities sum to one and the zero-based `score` is their probability-weighted mean. The provider's [OpenAPI schema](https://api.typesafe.ai/openapi.json), rechecked on 2026-09-28, instead says the values sum to *approximately* one. Neither specifies a numeric tolerance or display-rounding rule. The HTTP example uses string keys; the Python SDK's typed answer may use integer keys, which does not explain this raw HTTP result. Provider rounding is a plausible hypothesis, not an established exception. A client parser bug has **not** been demonstrated for this case. The adapter therefore rejects it with a typed error and invokes the existing complete local fallback when configured. Score remains experimentally isolated pending a provider contract clarification or a documented client-side rule supported by fresh diagnostics.

The human-readable reference says the probabilities sum to one while OpenAPI says approximately one. Please clarify response rounding precision, accepted mass tolerance, and whether the displayed probabilities and score must agree. We can supply the public request/response under a separately approved channel.” See the official [HTTP API](https://docs.typesafe.ai/api) and [Score semantics](https://docs.typesafe.ai/primitives/score).
