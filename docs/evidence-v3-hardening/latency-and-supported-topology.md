# Latency, admission, and supported topology

The production Jev adapter now reuses an HTTP client, assesses bounded windows up to configured `max_concurrency`, preserves candidate order, and applies one global deadline to permission checks, queueing, calls, retries, and results. Known 429/529 failures may retry once after bounded Retry-After; each dispatch takes another quota reservation. Auth, schema, malformed Score, and unknown transport outcomes are not blindly retried. The research runners disable automatic retries so their pre-dispatch ledgers match the number of requests. Local tests exercise ordering, retry accounting, and no auth retry.

In the approved synthetic pilot, two serial four-pair batches took 984 and 1,017 ms; two configured two-wide batches took 537 and 558 ms. Per-pair medians were Score 253.5 ms, support 268 ms, ranking 239 ms. This small warm comparison shows the scheduling effect for those inputs; it is not sustained capacity, p95/p99, a production SLA, or an end-to-end answer time. The 96-call pilot had no 429, overload, transport, or fallback events. The historical QASPER warm rerank p50 was TEI 46 ms versus serial Jev Noul 2,308 ms, a different workload/layout.

The subsequent [atomic-question probe](jev-atomic-options-probe.md) returned four Noul answers in one call with a 256 ms median among valid calls and global Choice with a 259 ms median. One first packed call timed out at 20 seconds and one Choice call failed validation. The synthetic ranking labels were too easy to show a quality advantage; bundled inference is not wired into production. These observations support a bounded design experiment, not a claim that every number of questions has equal latency or cost.

The service's Jev failure path already requests a complete TEI ordering, rechecks source access, and exposes requested provider, fallback provider, and degraded status. A fallback must not mix incomparable Jev and TEI numeric scores. Strict-support failure remains fail closed and does not release an unchecked answer.

The shared Jev quota is process-local and a single-worker topology guard remains in place. No multiworker coordinator, restart-safe aggregate accounting, tenant fairness proof, credential-epoch test, or sustained load acceptance was delivered. Do not set an acknowledgement flag to bypass that guard. An operational design for a later slice should use atomic reservations keyed by stable billing account plus credential epoch, separate purpose permissions from the shared spending cap, preserve uncertain dispatch spend after crash, bound queues and in-flight work, and fail closed if coordination is unavailable. This is a design requirement, not an implemented distributed feature.
